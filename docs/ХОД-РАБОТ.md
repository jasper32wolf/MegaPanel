## 1. Что это за проект

Изначально Site Panel был задуман как мультиарендная панель для агентства или вебмастера, которая:

1. хранит структуру сайтов как JSON-манифесты в PostgreSQL;
2. формирует сайты услуг по матрице «услуга × модификатор × гео»;
3. использует недорогой LLM только для короткого уникального ядра, остальное собирает локально;
4. выпускает статические HTML/CSS/минимальный JS через SSG;
5. управляет публикацией, доменами, SSL, индексированием и редиректами;
6. принимает лиды, шифрует PII и маршрутизирует заявки;
7. поддерживает несколько tenant и роли;
8. даёт операционные, SEO, security и FinOps-инструменты.

**Текущая граница первого релиза:** self-hosted панель на VPS для одного оператора. Единственный внутренний `tenant_id` пока сохраняется для совместимости существующей схемы, но создание tenants, публичная регистрация, роли, API keys, plugin marketplace, client approvals и Wayback mapper исключены из пользовательского и публичного API-контуров. Поддерживаемый путь: оператор создаёт сайты, подключает домены, публикует static release и получает лиды с доставкой на один webhook.

### 1.1. Границы терминов

| Термин | В этом репозитории |
|---|---|
| **Panel** | React/Vite-интерфейс администратора в `apps/panel`. |
| **API** | FastAPI-приложение и бизнес-логика в `apps/api`. |
| **Worker** | ARQ-процесс для доставки лидов, повторов webhook и DLQ recovery в `apps/api/app/worker.py`. |
| **Клиентский сайт** | Сгенерированная статика из `packages/ssg`, не React-приложение. |
| **Tenant** | Агентство/клиентский контур с логической изоляцией данных. |
| **Manifest** | Site-as-Code документ с страницами, блоками, контактами и темой. |
| **Block kit** | Версионируемый набор HTML/CSS-блоков и theme profile. |
| **Lead Hub** | API и таблицы лидов, consent и аналитики. |

### 1.2. Что проектом пока не является

- это не публичный production SaaS или клиентский кабинет;
- это не подтверждённая «установка в один клик» на чистом VPS;
- это не полноценный SERP-трекер, FIAS/GAR importer, plugin marketplace или IaC-комплект;
- это не подтверждённый PostgreSQL/RLS integration flow: single-operator application code использует единственного владельца, но full DB proof ещё нужен;
- это не подтверждённый публичный контур «форма на клиентском домене → лид в панели → webhook»: контракт и durable delivery реализованы, Docker/Caddy/browser smoke ещё не выполнен.

Полный исходный замысел и ТЗ приведены без сокращений в [Приложении A](#приложение-a-исходный-запрос-и-полный-промпттз).

### 4.4. RLS и tenant isolation

`0002` и последующие миграции включают `FORCE ROW LEVEL SECURITY` для части tenant-таблиц. Helper `set_tenant_rls()` существует, но вызовов в приложении нет. Следствия:

- запросы/insert к RLS-таблицам не имеют установленного `app.tenant_id` или `app.bypass_rls`;
- login, register, seed и обычные endpoint нельзя считать рабочими с production-подобной ролью БД;
- часть поздних таблиц вообще не получила RLS;
- ручные `.where(tenant_id == ...)` не заменяют правильно настроенный второй контур.

До integration-теста на реальном PostgreSQL статус multi-tenancy — **blocked**.

## 7. Критичные наблюдения аудита

### 7.1. Secrets и локальные настройки

В `.claude/settings.json` ранее присутствовал plaintext auth token. Файл исключён из Git и удалён из index, но локально сохранён для владельца рабочего окружения. **Token требуется отозвать/ротировать вручную**: обнаружение plaintext credential уже считается компрометацией. Marker credential найден как минимум в одном existing Git commit, поэтому до внешней публикации repository нужна отдельная согласованная процедура удаления секрета из истории; history rewrite не выполняется автоматически. Значение в документации намеренно не приводится.

### 7.2. Auth и authorization

- Базовый committed snapshot содержал публичный `POST /auth/register`, принимавший `role`/`tenant_id` от клиента, включая `superadmin`.
- В текущем **незакоммиченном** working tree добавлены single-operator bootstrap script, `0012_auth_sessions`, HttpOnly cookie sessions, refresh rotation и CSRF middleware; `register` убран из OpenAPI unit-проверкой.
- Эти изменения ещё не считаются verified: нужны migration + PostgreSQL + browser panel compatibility + login/refresh/revoke end-to-end тесты. В частности, прежняя Panel ожидает token в login response, поэтому UI flow необходимо сверить.
- API keys создаются, но authentication middleware для них не найден.
- Endpoint `publish/queue-index`, `ops/serp/{site_id}` и `panel/builds/{site_id}` не делают достаточной tenant-проверки на уровне handler; RLS сейчас не может считаться компенсирующим контролем.

### 7.3. RLS

- Helper установки tenant context не вызывается.
- Не все tenant-таблицы покрыты RLS (`analytics_events`, часть AI/panel/hardening tables).
- Public lead/consent flows требуют отдельной безопасной DB policy или trusted service role.
- Нужны integration-тесты на два tenant и отдельную app DB role без `BYPASSRLS`.

### 7.4. Docker, worker и edge

- Production Compose/worker image is structured to run `apps/api/app/worker.py`, whose release registry is limited to lead webhook delivery. Docker execution, retry/DLQ behavior and Caddy static delivery still need runtime proof.
- API and Caddy use the shared sites volume (`/app/dist` → `/srv/sites`); candidate/activation code is unit-tested, but real hostname delivery and Caddy Admin behavior are unverified.
- Production Compose exposes only 80/443; PostgreSQL, Redis, API, panel and Caddy Admin stay internal by configuration. Public port scan and TLS verification remain staging gates.

### 7.5. SSG и Block Factory

- HTML block сначала slot-filled, затем sanitizes — это полезно; но title, h1 и meta attribute не HTML-escaped.
- CSS tenant block сохраняется без sanitizer/validator.
- Kit templates опираются на inline `style`, `<details>`, `<summary>` и `<address>`, которых текущий allowlist полностью не сохраняет.
- Lead honeypot теряет скрывающий style/tabindex после sanitizer.
- Calculator block не имеет связанного JS.
- Build пишет прямо в `current`, поэтому не является atomic; auto-rollback при ошибке build отсутствует.
- Root canonical и sitemap строятся с риском двойного `/`.
- В тесте layout root имеется условие `... or True`, которое не проверяет ожидаемый path.

### 7.6. Lead, consent и analytics

- Generated form не содержит обязательный `site_id`.
- Обычный `<form>` отправляет `application/x-www-form-urlencoded`, а API ожидает JSON body.
- `form_ts` остаётся пустым и не заполняется JS.
- Relative `/api` на клиентском домене требует proxy или абсолютный `API_PUBLIC_URL`.
- Cookie banner и analytics pixel генерируются/объявлены, но не включаются в SSG page.
- Consent/analytics endpoint принимает tenant ID от клиента без верификации принадлежности site.
- Webhook subscriptions из panel не используются lead dispatcher; dispatcher читает contacts manifest.

### 7.7. Остальные несоответствия

- SSRF HTTPS fetch к pinned IP требует корректного TLS SNI; Nominatim fallback обходит guard.
- Audit chain строится без lock/serial queue и подвержен race condition.
- Rate limit process-local и доверяет `X-Forwarded-For` без trusted proxy policy.
- FinOps одновременно пишет в DB и process-local ledger, затем суммирует оба источника, поэтому стоимость может завышаться.
- DSAR delete при наличии идентификатора отзывает до 500 consent записей tenant, а не только записи конкретного субъекта.
- Media/uploads пишутся в относительный `uploads/`, не в смонтированный `/app/uploads`, что конфликтует с read-only container.
- CI устанавливает не все workspace-пакеты явным образом, а Ruff уже гарантированно падает на текущем baseline.
- Root `pyproject.toml` now includes `packages/block-library` as a `uv` workspace member/source; validate it in a clean `uv` environment before treating it as a full packaging proof.

### 7.8. GitHub release/recovery: текущие границы

- Добавлены `deploy-production.yml` и `recover-production.yml`, immutable releases, `current`/`previous`, forced-command SSH gateway, restic scripts и panel/API control plane. API разрешает только fixed workflows, `main`, verified SHA/action/snapshot, TOTP operator и audit-safe operation records.
- Deploy workflow fail-closed: запускается только после successful `ci.yml` SHA из `main`; текущий Ruff baseline делает CI red и тем самым блокирует автоматический deploy.
- Scheduled GitHub probe запускается каждые 10 минут как best-effort. Он сначала делегирует внутренний health check VPS release manager и не должен заменять независимый uptime monitoring.
- `auto-recover` допускает только bounded restart → code rollback. PostgreSQL/volume restore требует выбранный snapshot и literal `RESTORE` через manual GitHub workflow или panel dispatch; никакой путь не выполняет его автоматически.
- Caddy volumes получают права UID `10001` при bootstrap, а production Compose использует `nocopy`, чтобы Docker не копировал root-owned image data в эти volumes. Реальный VPS подтвердил initial Docker stack, restic backup и TLS; GitHub panel control и staging drill всё ещё не проверены runtime.
- Рабочий server bootstrap и restic destination уже подтверждены на VPS; GitHub Environments/control token custody, реальный panel dispatch и staging recovery/restore drill обязательны до включения этого control plane. См. `docs/runbooks/github-deploy-recovery.md`.

4. Любой security/production blocker записать в §7/§8 и P0/P1.

6. При новой migration обновить §4.3 и migration head.

## 3. Данные: Гео, Морфология, Дедупликация

### 3.1. Источники гео-данных

* **РФ:**
  * ФИАС / ГАР — официальный источник адресных данных.
  * КЛАДР — устаревший, только как fallback для исторических данных.

### 3.2. Морфологический движок

**Выбор инструмента привязан к стеку бэкенда (см. раздел 1):**

* **Python-стек (FastAPI):**
  * `pymorphy3` — активная поддержка, словари OpenCorpora, MIT-лицензия.
  * `pymystem3` — обёртка над бинарём `mystem`. Требует коммерческой лицензии; использовать только при наличии лицензии, иначе — `pymorphy3`.
* **Go-стек:**
  * Прямого бесплатного аналога `pymorphy3` для русского в Go нет.
  * Варианты:
    1. Sidecar-сервис на Python (`pymorphy3`) с gRPC/REST-интерфейсом — рекомендуемый вариант.
    2. `github.com/aaaton/golem` — Snowball-стеммеры (лемматизация, но не полная морфология).
    3. `mystem` binary — только при наличии коммерческой лицензии.
* **Другие языки:** `spaCy` / `Stanza` (Python) для лемматизации. Fallback — словарь исключений + базовые правила склонения.
* **Склонение в шаблонах:** переменные-плейсхолдеры с падежами (`{city_nom}`, `{city_gen}`, `{city_prep}`), автоподстановка в текст.
* **Согласование родов/чисел:** правила для каждой категории.
* **Кэш морфо-разборов:** Redis/PostgreSQL по хэшу словоформы.
* **Валидация:** запрет публикации при несогласованных формах.

### 3.3. Кросс-сайтовая дедупликация контента

* **Уровни проверки:**
  * Внутри одной страницы (нет дублей блоков).
  * Внутри одного сайта (нет почти-дублирующихся URL).
  * Между сайтами одного тенанта — критично для сеток.
  * Против публичного индекса (опционально: SimHash против crawl-выборки).
* **Алгоритмы:**
  * SimHash (64/128-бит) — быстрое сравнение целых страниц.
  * MinHash + LSH — для чанков/абзацев.
  * Shingling (n-gram, n=5..9) — нормализация текста (лемматизация, удаление стоп-слов) перед хэшированием.
* **Пороги (настраиваемые per-tenant):**
  * `similarity > 0.85` — блокировка публикации.
  * `0.70 < similarity ≤ 0.85` — предупреждение + авто-запрос на регенерацию уникального ядра.
  * `similarity ≤ 0.70` — ок.
* **Хранение:** `content_hashes (page_id, tenant_id, simhash, minhash_buckets, updated_at)`, индексы для LSH.
* **Автодействия при срабатывании:**
  * Перегенерация уникального ядра (Micro-Infill).
  * Перестановка блоков, замена синонимов, изменение FAQ.
  * Логирование в audit-log + уведомление менеджера.
* **Self-Audit Footprint Scanner:**
  * Собственный краулер проходит по сетке и ищет паттерны PBN-детекции: общие CSS-переменные, порядок блоков, шаблоны телефонов, IP-хостинг, whois-пересечения.
  * Назначение — только внутренняя оценка рисков оператора. Отчёт в панели с оценкой риска по каждому сайту; не является инструментом сокрытия следов от поисковых систем.
* **Content Decay Detector:**
  * Отслеживание падения трафика/позиций по страницам (через SERP-трекер из 7.5 и аналитику).
  * Автотриггер Evergreen Refresher или полной перегенерации при деградации.

## 5. AI Engine & Ультра-Экономный Токеновый Пайплайн

### 5.1. Сверхэкономная Архитектура Генерации (до 90–95% экономии)

* **Иерархическая Micro-Infill генерация:** LLM генерирует только уникальное ядро текста (50–100 токенов: уникальный оффер, 2–3 локализованных тезиса). Обвязка, FAQ, таблицы цен — локальный шаблонизатор.
* **Двухуровневая Матричная Сборка (Slot-Filling + Morphological Engine):** LLM создаёт базовые шаблоны с плейсхолдерами один раз на категорию. Локальный движок подставляет значения из гео-базы со склонением (см. 3.2).
* **Комбинаторно-Синтаксическая Мутация:** 10–15 базовых предложений на категорию + локальная сборка сотен страниц на графах синонимов и перестановок без API.
* **Model Tiering:**
  * Micro-LLM (мета-теги, краткие описания, структуры): Llama 3.1 8B / Qwen2.5 7B / Claude 3 Haiku.
  * Main LLM (уникальные экспертные статьи, офферы): DeepSeek-V3 / Claude 3.5 Sonnet.
  * Reasoning (сложный аудит, проверки, длинные статьи): DeepSeek-R1 / o1-класс — только когда reasoning реально нужен.
  * Формат вывода — плоский Compact JSON Schema.
* **Batch API Processing:** только если провайдер поддерживает Batch API и скидку; иначе — очередь с rate limit и приоритетами.
* **Prompt Registry & Versioning:** хранение промптов с версиями, A/B-тесты, откат.
* **LLM Response Cache:** кэш по хэшу `SHA256(prompt + model + params)` в Redis/PostgreSQL.
* **Token Budgets & Quotas:** лимиты на tenant/проект/категорию, алерты при превышении.
* **PII Redaction:** удаление/маскирование PII перед отправкой в LLM.
* **Failover Router:** по ошибке, стоимости и латентности (DeepSeek Chat → Claude Haiku → Llama 3 via Groq).

### 5.2. Валидация Контента и Защита (Validation & Safety Pipeline)

* **Structured Outputs Only (JSON Schema Mode):** строго валидный JSON, без генерации HTML напрямую.
* **Anti-Prompt Injection (OWASP LLM01):** валидация входных данных, экранирование управляющих конструкций.
* **CWE-1336 (SSTI):** отдельный класс угроз — защита шаблонизатора.
* **Content Linter & HTML Sanitizer (`nh3` / `bluemonday`):** детекция обрывков промптов, валидация топонимов (см. 3.1), очистка опасных тегов.
* **Evals & Quality Gates:** антиплагиат, фактчекинг, детекция галлюцинаций, проверка полноты интента. Регулярные прогоны — см. 15.
* **Dead Letter Queue:** для задач, не прошедших валидацию, с ручным разбором.

### 5.3. Расширяемый AI workspace для структуры, блоков и SEO

* Провайдерные API и credentials на первом self-hosted release общие для одного оператора VPS; не реализовывать клиентское управление ключами/ролями. Поддерживать проверенные native adapters, включая GLM/Zhipu, и OpenAI-compatible gateways (включая OpenRouter) с ручным model ID. Новый vendor не считается поддержанным до adapter contract tests.
* Ключи хранить только encrypted server-side через `FieldEncryptor`; API write-only/masked. Custom endpoints — HTTPS, без URL credentials, с проверкой allowlist, public DNS и ограничениями egress. Redirects запрещены; размер/время ответа ограничены.
* Free/price/capability сведения хранить как provider-reported/operator-verified metadata с source и timestamp. Не выбирать бесплатную модель автоматически и не обещать неизменность цены, quota, retention или uptime.
* Каждый генеративный action использует отдельный versioned Markdown prompt либо явно определённую chain. Хранить prompt ID/version/hash, input snapshot hash и eval fixtures; недостающие/конфликтующие факты не додумывать.
* AI получает только подтверждённые business facts, выбранные keywords/geography и разрешённый curated kit/block catalog. Никогда не передавать lead PII, credentials, cookies или secrets. Output — validated structured data, без произвольных HTML/CSS/JS, template code, routes или commands.
* Оператор явно выбирает provider/model, подтверждает внешнюю обработку и лимит расходов до запроса; estimate — оценка, provider-side spending cap обязателен для платной модели. Вызов, стоимость/usage и provenance аудируются.
* Архитектура, SEO brief, metadata, block sequence и content — отдельные reviewable artifacts. Human approval на каждом consequential boundary обязателен. Одобренная архитектура может создать только draft PagePlan; затем действуют существующие submit-review/approve, PageDraft QA, apply, candidate build, private preview и explicit publish gates.

## 7. Глубокий SEO-Модуль и High-Speed SSG

### 7.1. Programmatic SEO, Geo-RAG & Dynamic Drip-Publishing

* **Geo-RAG Enrichment:** уникальные станции метро, ориентиры, микрорайоны, зоны обслуживания, гео-отзывы (источник — гео-справочник из 3.1).

* **Источник истины по статусам:** PostgreSQL. Redis — кэш/очередь.
* **Thin Content Guard:** авто-`noindex` при недостатке контента или дублировании (см. 3.3).
* **Взаимодействие с Bulk Publish/Unpublish (17.4):** ручные операции меняют публикационный статус (`draft`/`published`/`archived`), но не отменяют drip-очередь индексации. Для принудительного снятия `noindex` — отдельное право `admin.force_index` с логированием в audit-log.

### 7.2. High-Performance SSG & In-Memory Manifest Cache

* **In-Memory Manifest Cache:** воркер считывает JSON-манифест из PostgreSQL в RAM один раз на старт сборки.
* **Pre-Compressed Assets (Brotli/Zstd):** авто-сжатие `.br`/`.gz` во время сборки. Caddy отдаёт через zero-copy.
* **Incremental SSG:** точечная пересборка только изменённых страниц.
* **Параллельный Worker Pool:** распараллеливание по ядрам CPU на компилируемых шаблонах.
* **Cache Headers / CDN:** `Cache-Control`, `stale-while-revalidate`, `s-maxage`.
* **Preview/Staging Builds:** отдельные сборки для клиентского ревью.

### 7.3. Векторная Перелинковка, Canonical & Technical SEO

* **Silo Link Matrix:** близость страниц внутри гео-узла (TF-IDF / векторный граф), динамические LSI-анкоры.
* **Canonical Guard:** `<link rel="canonical">` строго на саму страницу.
* **Core Web Vitals:** Minimal-JS / Progressive Enhancement, WebP/AVIF (`srcset`, `loading="lazy"`, `fetchpriority="high"`), Inline Critical CSS.
* **Hreflang & мультиязычность:** корректные `hreflang`, `x-default`, отдельные sitemap-индексы.
* **404 / 410 / Карта редиректов:** UI для управления, автоматическая генерация.

### 7.4. Индексация, API, Evergreen Refresher & Schema.org

* **IndexNow API:** Bing, Yandex, Seznam, Naver. Google — через Search Console API. Sitemap ping Google не использовать.
* **Robots.txt & Dynamic Sitemap Generator:** sitemap строго с URL в статусе `indexed`, чанкование по 10 000 URL, sitemap index.
* **AI Crawler Policy (настраиваемая):** training crawlers — блокировать, AI search/agents — разрешать через `/llms.txt` (опционально, per-tenant).
* **Zero-Token Evergreen Refresher:** локальный модуль — даты, год, плейсхолдеры цен каждые 6–12 месяцев без LLM.
* **Schema.org JSON-LD:** `LocalBusiness`, `Service`, `BreadcrumbList`, `FAQPage`. Валидация через Rich Results.

### 7.5. SERP-Трекер, Auto-Correction & Drop-Domain 301

* **SERP Self-Correction:** если страница не в ТОП-30 через 45 дней — перегенерация `<title>`, `<h1>`, FAQ + IndexNow.
* **Легальный SERP-трекер:** через официальные API (DataForSEO / SerpApi / Yandex XML).
* **Wayback 301 Mapper:** парсинг ссылок дроп-доменов, настройка 301 через Caddy Admin API.

## 9. Multi-Client Lead Hub (ИИ-Квалификация и Маршрутизация)

* **Маршрутизация:** Telegram, Email, Webhooks в AmoCRM/Bitrix24 с подписью HMAC-SHA256.

* **ИИ-Квалификация:** лёгкая LLM отсекает B2B-спам и коммерческие предложения.
* **Encrypted LocalStorage Buffer (осторожно):**
  * Хранить только минимум PII; ключ шифрования в JS не является секретом.
  * TTL 24 часа, обязательное согласие, автоочистка.
  * Альтернатива: IndexedDB + WebCrypto с non-extractable ключом.
* **Dead Letter Queue** для неотправленных вебхуков + retry с exponential backoff.
* **Rate Limiting** на лид-формы и API.

### 9.1. CAPTCHA-альтернативы

* **По умолчанию — без CAPTCHA:** honeypot + time-lock + dynamic token + IP-репутация уже покрывают большинство ботов.
* **Cloudflare Turnstile** — приватная альтернатива без слежки, лёгкая интеграция, есть invisible-режим.
* **hCaptcha** — приватная альтернатива с enterprise-планом и accessibility-режимом.
* **Не использовать Google reCAPTCHA по умолчанию** — приватность, GDPR/152-ФЗ, тяжёлый скрипт, влияние на Core Web Vitals.
* **Progressive Challenge:** CAPTCHA включается только при подозрительном поведении (высокая скорость, повторные отправки, «плохой» IP).
* **Accessibility:** обязательно fallback для screen-reader и keyboard-only.
* **Логирование:** все срабатывания challenge → Redis Stream + аудит.

## 12. Модуль Комплексной Безопасности (Enterprise Security)

### 12.1. Аутентификация и Авторизация

* Argon2id + Pepper, обязательный TOTP/WebAuthn, rate limiting с экспоненциальной задержкой.
* RBAC + ABAC.
* **Tenant IDOR Guard (CWE-639):** проверка `tenant_id` в middleware и PostgreSQL RLS как второй контур.
* **Secret Management:** Vault / Docker secrets / SOPS, ротация ключей.

### 12.2. Сессии, Токены и Валидация

* Cookies (`HttpOnly`, `Secure`, `SameSite=Strict`), CSRF-токены.
* **JWT:** короткоживущий access + refresh rotation с reuse detection. Blacklist в Redis — только для access-токенов до `exp`.
* **Strict CSP без `unsafe-inline`** (генерируется per-tenant на основе домена тенанта — для white-label):
  ```
  script-src 'self' 'sha256-...';
  style-src 'self' 'sha256-...';
  connect-src 'self' https://api.<tenant-domain>;
  object-src 'none'; base-uri 'self'; frame-ancestors 'none';
  ```
* **Security Headers:** HSTS, X-Frame-Options, Referrer-Policy, Permissions-Policy, COOP/COEP/CORP.
* **CORS** для lead API (строгий allowlist origin per-tenant).
* Prepared Statements (SQLi), защита от SSTI, XXE, Path Traversal.
* **Rate limiting** с раздельными бюджетами для auth, lead, API.

### 12.3. Изоляция сети и Данных (Egress Traffic & Blind Index PII)

* **Egress Traffic Filtering:** forward-proxy с allowlist по доменам и SNI, IP-allowlist как дополнение. Периодическое обновление IP LLM-провайдеров через их API.
* **Field-Level DB Encryption & Blind Index:** AES-256-GCM для PII + `HMAC-SHA256(phone + Blind_Index_Pepper)`.
* **HMAC-SHA256 Webhook Signing** для всех исходящих вебхуков.
* **PITR & Backups:** регулярные бэкапы PostgreSQL с point-in-time recovery, шифрование бэкапов, тесты восстановления.

### 12.4. Загрузка файлов, Защита от ботов и Логирование

* Whitelist расширений, Magic Bytes, рекодинг изображений (Pillow/VIPS), лимиты размера.
* **FCRDNS Bot Verification:** проверка Googlebot/YandexBot по Forward-Confirmed Reverse DNS — до bot-whitelist, но после базовой IP-репутации и общих rate limits.
* **WAF:** CrowdSec + ModSecurity/Coraza.
* **Single-Threaded Hash-Chained Audit Log:** однопоточная очередь Redis + PostgreSQL, `SHA256(запись + прошлый_хэш)`.

### 12.5. Incident Response, Supply Chain & Advanced Security

* **Incident Response Plan (IR):**
  * Классификация инцидентов (P0–P3), каналы связи, роли (IR-lead, comms, legal).
  * Уведомление Роскомнадзора по 152-ФЗ — в течение 24 часов (ст. 21 ч. 3.1).
  * Уведомление субъектов ПДн по GDPR — в течение 72 часов.
  * Регулярные tabletop-учения, postmortem-шаблон без поиска виноватых.
* **Penetration Testing:** ежегодный внешний пентест + после крупных релизов; отчёт и трекинг фиксов.
* **Vulnerability Disclosure Policy (VDP):** публичная страница `/.well-known/security.txt`, контакт для исследователей, safe-harbor для добросовестных.
* **SBOM + Supply Chain Security:**
  * Генерация SBOM (Syft) для всех артефактов.
  * Подпись артефактов (cosign / Sigstore), верификация при деплое; ключи cosign — в Secret Management (12.1).
  * Сканирование зависимостей (Trivy, Grype) в CI, блокировка релиза при critical CVE.
* **Runtime Security:** Falco / Tetragon для детекции аномалий в контейнерах (shell в проде, неожиданные syscalls, сетевые соединения).
* **Secrets Rotation Automation:** автоматическая ротация ключей LLM, БД, webhook-секретов по расписанию.
* **Admin Session Anomaly Detection:** невозможные перемещения, новые устройства, новые гео → step-up auth.
* **Anti-Phishing для панели:** брендированные письма, DMARC `p=reject`, обучение пользователей.
* **Data Retention Matrix:** таблица «тип данных → срок хранения → основание → способ удаления» для PII, логов, лидов, аналитики. Автоматическое удаление по истечении.
* **DSAR Automation (Data Subject Access Request):** автоматическая выгрузка/удаление данных субъекта ПДн по запросу, с журналом и подтверждением.
